Leash: system design

A wallet control layer that decides whether an AI shopping agent may spend a customer's money, with a permission assistant that proposes rules for customer review. Product search and order preparation belong to an external shopping agent.

Scope updated 2026-09-25. This is a design, not a completion report. The current product agreement and DEC-033–037 govern permission context, draft revisions and external-agent handoff. An optional local Laya fact-reader adapter is implemented for experiments and defaults to shadow mode. Its quality gate has not passed; the deployed worker has not been switched. See the measured results and remaining gaps.

Every team decision and assumption behind this design is in the decision log; DEC- numbers below refer to it.

Rules decide, models advise

Deterministic checks own every verdict. Laya can only add caution, never approve.

Shop text is data

Nothing in item_details or the agent's request can change the mandate.

Nothing bypasses the engine

The permission LLM cannot activate mandates, start purchases or call decision endpoints. External checkout events pass through the control engine.

Predictable when degraded

Model down means regex only; a fact a rule needs but regex can't establish follows the uncertainty policy. Deadline close means a safe step_up, never silent approval.

Components and trust boundaries

The live permission conversation uses strict structured LLM output and deterministic guardrails (DEC-063): schema validation, supported rule fields and values, customer-source attribution, catalogue identities, contradiction checks and revision-bound human confirmation. Typesafe/Jev is not part of this flow. The English grammar is confined to the explicit offline/reference path and cannot add rules or questions to live model drafts. Invalid output saves no proposal; unresolved conditions block submission. The review shows both enforced rules and unrestricted fields, because type safety alone cannot prove the model understood every condition.

Ordinary chat, history questions, clarification answers and permission changes are separate intents (DEC-062). The task instruction stays visible, and simulator submission preserves its exact text while answers refine reviewed hard rules. Unconfirmed revisions may correct earlier readings; active mandates only tighten and submitted platform drafts remain immutable. New mandates do not inherit unrelated mandates’ limits.

What happens to one purchase

Laya classifies evidence for the rules. It reads what merchant data says about extra services, future charges, returns and instructions aimed at the payment system. These are typed observations, tied to the cart line; they carry no spending authority. Classification establishes what the text claims, not whether the merchant will honour it.

Current integration: add-on flags feed the basket rule, final-sale flags feed the returns rule, and payment-steering flags feed the shop-text rule. Recurring-charge flags are observed but have no separate rule yet. Semantic item matching remains planned: it needs the confirmed requested product, which the reader currently does not receive. Numeric sizes and return days still use deterministic extraction; absent facts remain unknown. Tests must score classification errors and resulting verdicts separately—a stricter decision can still be a false alarm.

State that the engine remembers

Every verdict depends on earlier ones. The state store keeps five records, all keyed by the live authorization_id or the card, and all timed by simulated purchase time, never the real clock.

Field names in hard_rules that are ours use the versioned leash. registry, e.g. leash.merchant.prior_purchases.v1 (DEC-004). The API only stores them; the engine defines what they mean, and an unknown field never approves (DEC-005).
